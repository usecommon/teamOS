Human teams · Agent fabric

Human teams.
Agent fabric.

Team OS gives every person on a team a proactive agent — one that works on their behalf without being asked. Drafts arrive done. Loops fire on the world's schedule. Everything under gates, on the record, improving over time. The agents are the connective layer that carries what the team knows.

What it is

A team of agents — one per person — not another agent to babysit.

Most "agent" tools ask you to manage the agent. Team OS inverts it: the agent manages the busywork for you, and does it before you ask. In a single-user setup a member can itself be an agent — but the point is the human team, and the fabric that connects them.

◆

Proactive

It compiles your recurring work from your own history, then drafts it on schedule — unrequested. You react ✓ or ✗; it learns.

▤

On the record

Ten hash-chained ledgers record every decision, every write's lineage, every human signal. A mutated record breaks the chain.

⌘

Under gates

A single hook inspects the payload of every tool call — not just its name — before it runs. Autonomy widens slowly on your ✓, narrows instantly on a ✗.

⇄

It transfers

A skill one person's agent gets good at can be promoted — through a signed gate — into a teammate's agent. That crossing is the fabric.

◱

Yours to steer

Team OS dictates nothing about what it reads or how it's used. Sources are opt-in, off by default; policy is configuration you hold, never opinion it holds.

⏏

Yours to leave

Everything is plain files in git. Leave with git clone and you keep your scope, decryptable by your key alone.

The MCP door

Team OS exposes read tools and propose_* tools over MCP. Reads are read-only; proposals land in an inbox, never the corpus. A deterministic gate processor is the only writer.

From Claude, via the door

Inside Claude you can browse the corpus, query skills, and file proposals — all through the door, all gated and ledgered. The door never writes your stores directly.

Owned inference (Plane A)

Team OS's own connectors run on inference you own — an API key or a local model — so it can operate independent of, and excluding, your Claude account.

The fleet

Eight agents, each owning a slice of the work.

A member need not be human. Every agent has a role, a scope, jobs it owns, and an automation trigger — and every one is monitored, auditable, and haltable.

Features

Initiative first, interface second.

✦

Day One Brief

On cold start the agent compiles your recurring work and delivers an unrequested brief — a job draft you accept per-line with a ✓/✗ reaction.

↻

Autonomous loops

Recurring deliverables get drafted on their own cadence — weekly digest, standup, status update, release notes — before you ask, checkpointed so a mid-run kill resumes.

↗

Learning

Signals (L8) become scores (L7), scores become skill versions (L6). Watch each skill's quality climb version over version — and see what improved.

☑

Recommendations

Agents propose actions to you — link this entity, schedule this task, add a review step. They never act on their own; they wait for your Accept.

◈

Insights & discovery

The scout watches what recurs and what improves, then proposes a new skill or an action. Nothing is created until you accept it.

⛉

Circuit breaker & safety

A deterministic safety agent trips a breaker on any threshold breach; while open, every side-effect is denied fleet-wide. Only a human resets it.

▦

Fleet dashboard

Every agent at a glance — status, tasks done, acceptance, quality, subagents, health — plus a full per-agent profile of jobs, live tasks, and automation.

⇄

Skill transfer

Promote a proven skill through a signed gate (PII scan + eval floor + reviewed diff) into the team registry, where a teammate's agent picks it up.

▤

Full audit

Gate ledger says why every call was permitted; lineage ledger labels every write with source, evidence, transformation, and confidence.

Use cases

Role-ready on day one, not after weeks of ramp.

A role template is the provisioning unit: instantiate one and a member's agent starts with the specialized skills and knowledge already loaded.

Engineer

Ship with the busywork pre-drafted

  • Release notes and status updates drafted from your commits and PRs.
  • Code reviewer flags bugs, security, and convention drift on every PR.
  • Standup written from what actually moved, waiting for your ✓.
Product / PM

Keep the team's knowledge current

  • Weekly digest compiled across your eligible sources, unprompted.
  • Researcher answers cross-source questions, verified and cited into the corpus.
  • Meeting summaries with decisions, owners, and follow-ups extracted.
On-call

A brief that meets the world's schedule

  • Loops fire on the incident's clock, not yours — draft-ready when you wake.
  • Every action gated and ledgered, so the paper trail writes itself.
  • Circuit breaker halts the fleet the moment something looks wrong.
Whole team

Skills that compound across people

  • What one agent gets good at transfers — through a signed gate — to the next.
  • Dashboards render per-skill, never person-vs-person. No individuation surface.
  • A leaver takes their scope with git clone; shared skills stay.

Policy-neutral, by construction Team OS never dictates a source or a use. It enforces exactly the configuration you set — never refusing a source you allow, never adding one you didn't. Source eligibility is your rule to hold; the tool's job is to respect it and record that it did.
Trust model

The controls are the product.

Gate inspects payloads
A permitted tool — Bash, Write, an MCP call — can't become an exfil path. The gate looks inside the action: egress scans, sensitive-read scans, a cloud-synced write treated as a send, an always-on outbound-content scan.
Files are truth
Corpus, skills, profile, templates are plain files in git. Databases and indexes are derived and rebuildable, never authoritative.
Lineage on every write
Every memory or corpus write carries source, evidence, transformation, confidence. An unlabelled write is rejected by construction.
Untrusted content ≠ plan
External and historical content can be summarized — it can never add a step, change a recipient, or trigger a tool without confirmation. Values, never structure.
Authenticated signals
Only the principal's verified identity counts a ✓. A forged reaction can never widen autonomy — that line is the one third-party attack chain's control.
Deletion before ingest
Erasure over the lineage graph is proven before any colleague data is ingested. Per-principal stores are encrypted; keys live outside the repo.
No individuation
Dashboards and reports render per-skill, never person-vs-person. There is no comparative surface.
Exit = clone
Leave with git clone and you hold everything in your own decryptable scope plus the shared artifacts you're keyed for. Nothing traps you.
Install & onboarding

Everything runs on your own footprint.

No collaborator data, no account policy. The gate hook runs on your machine with hook privilege — you review it before you activate it. That review is your control over your own trusted computing base.

Prerequisites

Python 3.10+, git, and Claude Code (runtime of record: Claude Code Desktop + local scheduled tasks). For unattended loops: owned inference — an API key or a local model — and a machine that stays on.

Clone & install

git clone https://github.com/usecommon/teamOS.git
cd teamOS
python3 -m pip install -r requirements.txt
make test        # schema + mapping gates should pass

Review the hooks — your security control

Read hooks/gate.py (~200 lines, ~15 min) against hooks/BEHAVIOR.md, the one-page spec the code must match: the decision table, "no network / no language model", reads only stdin + policy + the ledger it appends to. Proceed only if satisfied.

Activate the gate

Merge hooks/settings-fragment.json into .claude/settings.json to register the PreToolUse hook, then verify.

python3 scripts/teamos.py doctor      # "gate activated: yes"

Configure your sources (opt-in, policy-neutral)

In config/connectors.json: set inference to your backend; add sources with enabled:false until you want them read; set the Slack DM target to your own authenticated user id — the only identity whose ✓/✗ counts.

Set your encryption key (outside the repo)

mkdir -p ~/.teamos/keys        # NOT inside the clone

crypto_store.py refuses a key dir inside the repo by construction — the exit-equals-clone invariant depends on it.

Compile your footprint

python3 scripts/teamos.py compile \
    --footprint <dir-of-your-artifacts> --cc ~/.claude --out stores

You get a job graph, skills imported from your Claude Code commands, and a profile from your CLAUDE.md. Injected content is quarantined; raw ingest is discarded.

See your Day One Brief, then run the loops

python3 scripts/teamos.py brief --out stores   # dry-run render
python3 scripts/teamos.py loop  --out stores   # one pass → shadow drafts

For the real thing, register the loop as a local scheduled task on your always-on machine. Each run is checkpointed and anchors its chain heads off-box.

Verify integrity anytime

python3 scripts/teamos.py verify      # every ledger chain verifies
For collaborators — before your data flows You additionally sign a one-page data notice and receive shared skills only through the promotion gate (PII scan + eval floor + signed review). Your personal store is encrypted with your key; no one else can read it, and any read of it lands in your own access feed.
