What the schematic makes obvious

There is exactly one place everything that acts must pass: lane 3, the gate — and exactly one floor everything lands on: lane 4, the record. That's why the two must-build screens are the approval prompt (decide, at the gate) and the ledger explorer (trust, at the record). The dials feed the gate from the side; the door is an API off lane 1; the mechanisms in lanes 2 & 6 mostly run headless. A screen earns its place where a human has to touch the loop — nowhere else.

So — what actually gets a screen

Idea generation is generous; the build is disciplined. The honest read from the schematic.

Build, in this order

  1. 1Approval prompt (gate — lane 3)The thesis made visible; weakest today. ↗ prototyped.
  2. 2The dials editorA UI over policy files that already exist. ↗ prototyped.
  3. 3Ledger explorer + compliance export (record — lane 4)“Trust me” → “inspect it.” Unlocks the regulated buyer. ↗ prototyped.
  4. 4Connect-sources wizard + footprint reviewCold start; the first hour decides adoption. ↗ prototyped.
  5. 5Health / doctorCheap, high-trust; watches the whole loop. ↗ prototyped.

Deliberately not a screen

  • ✕The door (Plane B)An API off lane 1 — propose-only. No screen to own.
  • ✕Ledger writes & commit pathDeterministic, hook-gated code (SE-1/CN-2). A model never decides; a UI never writes.
  • ✕Any per-person comparisonNo individuation surface — per-skill only, never a leaderboard. Invariant, not preference.
  • ✕A big central consoleFiles are truth; screens are thin, rebuildable views. Don't build state that breaks exit = clone.
